Notes for whoever runs these:

- **From Claude Code inside VS Code, clear `ELECTRON_RUN_AS_NODE` first** (`Remove-Item Env:ELECTRON_RUN_AS_NODE`). That shell inherits `ELECTRON_RUN_AS_NODE=1` from the editor, which makes Electron start as plain Node and fail with `Cannot read properties of undefined (reading 'isPackaged')`. A normal terminal is not affected.
- To inspect the running app from a script, use `pnpm exec electron-vite dev --remoteDebuggingPort 9222` and talk to it over the DevTools protocol. `electron-vite preview` does not accept that flag; to run the built app with it, run `pnpm build` and then `node_modules\electron\dist\electron.exe . --remote-debugging-port=9222`.
- This machine runs other projects' Python and `uv` processes. When checking for or killing leftover engine processes, match on `-m pdfengine` in the command line; never act on `python.exe` by name alone.
- Development uses its own settings folder, `%APPDATA%\PDFnix-dev` (the installed app will use `%APPDATA%\PDFnix`). Recovery copies are in its `recovery` subfolder; delete them there to stop the recovery offer during testing. `PDFENGINE_RECOVERY_DELAY` (seconds) shortens the 2-minute wait when running the engine by hand.
- Native dialogs (Save As, "Save changes?") cannot be clicked over DevTools. In phase 3 they were driven with `WScript.Shell` `AppActivate('Save As'` / `'PDFnix')` + `SendKeys`; Alt+F4 to the main window (activate it by its process id) tests the real close path. A page-initiated `window.close()` does **not** go through it (see Verified facts).
- Phase 6 lessons for scripted runs: in Open/Save dialogs press **Alt+N** before typing (the File name box; `SendKeys('^a')` arrived as a literal "a", and once the focus was in the file list, so a picture from the user's own Pictures folder was chosen — nothing was written, but type only into the name box). The window is often `visibilityState: hidden` while scripting, so closing dialogs stay in the DOM with `data-state="closed"`; select `[role=dialog][data-state=open]`. CDP Enter must be `keyDown` with `text: "\r"` to submit a form. Before launching, check that no earlier PDFnix instance holds port 9222 and the single-instance lock (one from the phase 5 session was still running).
- "Microsoft Print to PDF" prints to `PORTPROMPT:`: SumatraPDF's silent print still opens a "Save Print Output As" window; answer it with Alt+N, the path, Enter.

| Does PyMuPDF journalling cover all edit types for undo/redo? | **Yes for phase 3's edits**: highlight/underline/strikeout/note creation, colour, opacity, contents, `set_rect` (move), `delete_annot` and `set_rotation` all undo and redo exactly; xrefs survive undo/redo; a new op after undos discards the redo steps; an op that changes nothing records no step; 200 ops + 200 undos take ~30 ms. `save(garbage=3)` and `tobytes` work with the journal on and keep the history. **Caveats:** (1) with the journal on, *any* change outside `journal_start_op`/`journal_stop_op` raises `FzErrorArgument: Can't alter an object other than in an operation` — and PyMuPDF's `Page.get_textpage`, `get_text`, `search_for`, `get_image_info` and `get_texttrace` call `set_rotation(0)` temporarily on rotated pages, so they fail there.
